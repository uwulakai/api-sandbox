# E2E: проверка запущенного API Sandbox

Тесты выполняют настоящие HTTP-запросы к `API_BASE_URL`, а не вызывают приложение
через TestClient. Docker и исходники backend для HTTP-прогона не нужны.
Публичный адрес каждого мока берётся из ответа API (`public_url`).

## Запуск вручную

Из корня репозитория, Python 3.12+:

```powershell
python -m venv e2e/.venv
e2e/.venv/Scripts/python -m pip install -r e2e/requirements.txt
$env:API_BASE_URL = 'https://api.api-sandbox.merlant.xyz'
e2e/.venv/Scripts/python e2e/run.py
```

Без `API_BASE_URL` runner не запускается. Можно указать любой свой тестовый стенд.
Опционально: `E2E_WAIT_SECONDS=90` (ожидание worker), `E2E_HTTP_TIMEOUT=15`
(таймаут HTTP-операций), `E2E_REPORT_DIR` (каталог отчётов).
HTTP(S)-прокси из переменных окружения не используются; проверка TLS включена.

Только доступность и отклонение запросов без авторизации, без создания данных:

```powershell
e2e/.venv/Scripts/python e2e/run.py -k 'health or authentication_required'
```

Либо Docker-runner без Jenkins:

```bash
docker build -t api-sandbox-e2e ./e2e
docker run --rm -e API_BASE_URL=https://api.api-sandbox.merlant.xyz \
  -v "$PWD/e2e/reports:/reports" api-sandbox-e2e
```

У Docker-runner `/reports` — один каталог текущего прогона: для сохранения истории
монтируйте отдельную папку на каждый запуск. Локальный runner автоматически
создаёт `e2e/reports/<UTC-время>-<run-id>`, Jenkins — каталог номера сборки.

## Покрытие

В `tests/test_live.py` находятся 13 pytest-проверок, объединяющих сценарии:

- Health, регистрация, повторная регистрация, login, неверный пароль, me, logout,
  отклонение отозванного/невалидного токена и запросов без токена.
- CRUD Mock, ожидание `running`, версия конфигурации, доступность API после старта.
- CRUD endpoints, нормализация пути/метода, конфликт `method + path`, разные методы.
- Публичные JSON, HTTP-статусы, заголовки, неизвестный путь/метод.
- Обновление ответа, задержка, выключение/включение и удаление endpoint.
- Stop/start/restart, изоляция пользователей и независимые ответы двух моков.
- Валидация, удаление работающего мока, исчезновение из API и недоступность runtime.
- Отдельная опциональная проверка физических Docker-контейнеров.

После обновления проверяется не только `running`, но и фактический новый ответ.
По умолчанию первый сбой останавливает дальнейшие тесты (`--maxfail=1`), затем
выполняются finalizers. Это ограничивает каскад запросов к недоступному стенду.
Для диагностического полного прохода можно передать `--maxfail=0`.
Автоматических повторов изменяющих запросов нет.

## Данные и очистка

`full` создаёт два пользователя с уникальными email `e2e-…@example.com` и случайными
паролями; моки создаются только у этих пользователей. Чужие данные не изменяются.
В конце каждого теста удаляются известные ему моки, в конце прогона отзываются
полученные токены. **Пользователи остаются в БД:** удаления аккаунтов в API пока нет.
Периодические full-прогоны будут накапливать аккаунты; предпочтителен тестовый стенд.

Если запрос создания завершился таймаутом, сервер мог успеть записать данные.
Для такого мока finalizer пытается найти запись по уникальному имени у того же
тестового пользователя и удалить её; повторный POST не выполняется.
Если сеть/API недоступны или процесс принудительно убит, очистка не гарантируется.
`resources.json` содержит email, имена/ID моков и результаты очистки, включая
`creation_result_unknown` и `registration: unknown`; это не успешное удаление.
`api_deleted: true` подтверждает только исчезновение из control-plane API.
Публичный 404 не доказывает физическое удаление контейнера из Docker.
Секреты не сохраняются, поэтому после потери процесса автоматическое восстановление
его сессии для очистки невозможно; понадобится доступ администратора к стенду.

## Отчёты

- `report.html` — самостоятельный HTML-отчёт.
- `junit.xml` — результаты для Jenkins, история и график тестов.
- `console.log`, `requests.log` — ход тестов, HTTP-статусы, длительности, request ID.
- `resources.json` — созданные/возможно созданные ресурсы и состояние очистки.
- `run.json` — идентификатор прогона, код завершения и время UTC.

Тела запросов/ответов, query string, заголовки авторизации и пароли в журнал запросов
не записываются. Не включайте pytest `--showlocals`: локальные переменные тестов
содержат временные пароли/токены. HTML/JUnit предназначены для закрытого интерфейса.

## Границы HTTP-проверок

`E2E_DOCKER_INSPECT=1` включает проверку двух разных контейнеров, labels, health
и физического удаления. Ей нужен доступ к Docker daemon **того же стенда** через
стандартные настройки Docker SDK. По умолчанию она `SKIPPED`; у Jenkins нет такого
доступа. Не публикуйте Docker API в интернет и не подключайте socket ради HTTP-тестов.

Этот набор не делает `docker compose down/up`, не рестартует production API,
не проверяет состояние одноразового `mock_runtime_image` и не перезапускает чужие моки.
Проверка shutdown/startup всего Compose требует отдельного одноразового стенда
и управления его Docker/Dokploy; она не может быть выполнена только по URL API.

## Проверка самого тестового инструмента без сети

```powershell
e2e/.venv/Scripts/python -m pytest -c e2e/pytest.ini e2e/unit
```

Для браузерного запуска и расписания см. [Jenkins](../automation/README.md).
